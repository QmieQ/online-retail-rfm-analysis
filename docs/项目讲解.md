# 项目详细讲解与答辩准备

## 一、这个项目解决什么问题

项目有两条线。一条是销售分析：销售额什么时候高、订单平均金额是多少、哪些商品贡献较多。另一条是客户分析：哪些客户最近购买、购买次数多、累计金额高，如何给不同客群制定后续验证方案。

完整流程为：原始 Excel → 数据质量检查 → 类型规范化 → 明细清洗 → 订单/月度/商品汇总 → 客户 RFM → MySQL 独立核对 → 图表与报告。

实际结果在 `outputs/analysis_report.html`，本文件重点讲原理、实现和答辩。

## 二、先理解一行数据代表什么

| 原始字段 | 中文含义 | 使用方法 |
| --- | --- | --- |
| InvoiceNo | 发票/订单编号 | 识别不同订单；C 开头表示取消 |
| StockCode | 商品代码 | 商品汇总主键 |
| Description | 商品描述 | 展示名称，有缺失和名称变体 |
| Quantity | 明细数量 | 与单价相乘；负数常见于冲销 |
| InvoiceDate | 发票日期时间 | 月度归属、最近购买日期 |
| UnitPrice | 单价，英镑 | 保留原始小数精度 |
| CustomerID | 客户编号 | 客户关联键；不是可求平均的数字 |
| Country | 客户国家 | 地区汇总 |

最重要的区别是：**一行不是一张订单，也不是一位客户。** 同一张订单买了三种商品，通常至少有三行。因此订单数用 `nunique()`，不能用明细行数。客户 ID 作为字符串保存，避免 `17850.0` 这样的浮点展示。

## 三、为什么要清洗

### 1. 缺失值

缺客户编号会影响客户分层，但不妨碍已知数量和单价的交易贡献销售金额。因此销售口径保留这些明细，客户口径再排除，不能为了 RFM 一开始就把这些销售全部删除。

缺描述不等于缺商品代码。按 StockCode 汇总仍然有效。日期、数量、单价等计算必要字段无效时则剔除。

### 2. 重复值

按规范化后的原始八字段完全一致去重，保留首次记录。不能仅按 InvoiceNo 去重，否则会把同一订单里的其他商品误删。源行号 `source_row` 对应 Excel 的实际行号（表头为第 1 行），方便回查。

完全重复行是否一定是导出重复？无法绝对确定。本项目把它作为清洗假设，并提供重复行数量，答辩时应说明这一点。

### 3. 取消、负数与零值

主分析研究有效正向交易，所以排除 C 开头的发票、数量≤0 和单价≤0。每行只分配一个主要原因，按“重复→必要字段无效→取消→数量→价格”的顺序判断，所以清洗表各类行数能够相加还原原始总数。

这不代表这些记录没有业务意义。完整审计文件保留了所有记录，报告另算含冲销的有符号金额，并提供客户金额敏感性表。不能把正向金额直接说成净收入。

### 4. 金额精度

如果直接对二进制浮点数相乘求和，可能产生非常小的舍入差异；如果先把三位小数单价四舍五入到两位，又会改变源数据。这里把价格乘 10,000 转成整数，再乘数量并汇总，展示时除以 10,000。例如 1.005 英镑 × 2 件 = 20,100 内部单位 = 2.01 英镑。价格超过四位小数时程序报错，避免静默截断。

## 四、销售指标怎么计算

```text
明细金额 = 数量 × 单价
正向销售额 = 有效正向明细金额求和
订单数 = 有效明细中不同 InvoiceNo 的数量
订单平均金额 AOV = 正向销售额 ÷ 订单数
商品贡献率 = 该商品正向金额 ÷ 全部标准商品正向金额
月度环比 = 本月销售额 ÷ 上月销售额 - 1
```

严格说这里的 AOV 是“每张有效订单的平均金额”。中文电商语境里的“客单价”有时指每位购买客户平均金额，有时指每单金额，因此项目使用“订单平均金额”避免歧义。

月度销售按明细 InvoiceDate 所在月份统计，不能把订单明细数量当订单数。2011 年 12 月只到 9 日，不对它计算完整月环比，不能直接据此判断业务下滑。

商品排名剔除 POST、DOT、M 等非标准代码，避免把运费或手工收费直接解释成热销商品。正则只是分类代理规则，实际业务应使用正式商品主数据。主销售额仍包括这些正向收费，因此商品金额小计与总销售额不同，差额可从 non_merchandise.csv 核查。

## 五、RFM 从例子理解

假设观察窗口结束后的基准日为 2011-12-10，客户 A 最后购买日期是 2011-12-08，观察期内有三张不同订单，正向金额合计 500 英镑：

```text
R = 2 天
F = 3 单
M = 500 英镑
```

R 越小表示最近仍在购买；F 越大表示购买次数较多；M 越大表示历史正向金额较多。把三个维度分开，才能区分“一次买很多”的客户和“经常买”的客户。

本项目用源数据最大日期的次日作为基准日，因此固定数据重跑会得到相同 R。若使用今天，所有老数据客户都会看起来几千天没有购买，而且结果每天变，不适合这个历史快照。

### 评分方法

先在全部可识别客户中计算 20%、40%、60%、80% 分位点。每个值对应 1–5 个数值档位，R 反向评分。边界规则写在代码中：只有严格大于一个阈值才向上越过一档。

例如 F 阈值假设为 `[1, 2, 3, 5]`，则 F=1 得 1 分，F=2 得 2 分，F=3 得 3 分，F=4/5 得 4 分，F>5 得 5 分。**这只是示例，实际阈值看 metrics.json 或正式报告。**

如果某几个分位点都等于 1，意味着只买一次的客户非常多。相同 F 必须同分，因此某些评分档会没有人，档位人数也不一定各占 20%。不使用 `rank(method='first')` 强行按行号拆开相同频次。

### 八类客户规则

评分≥3定义为高，评分≤2为低。这里的高低是相对本批客户的规则，不是行业通用标准。

| 客户类型 | R 分 | F 分 | M 分 | 解释 |
| --- | --- | --- | --- | --- |
| 重要价值客户 | 高 | 高 | 高 | 较近购买、较多次、较高金额 |
| 重要发展客户 | 高 | 低 | 高 | 近期购买较多金额，次数偏少 |
| 重要保持客户 | 低 | 高 | 高 | 历史购买较多，但最近不活跃 |
| 重要挽留客户 | 低 | 低 | 高 | 金额高但次数少且较久未购买 |
| 一般价值客户 | 高 | 高 | 低 | 活跃且频次较高、金额偏低 |
| 一般发展客户 | 高 | 低 | 低 | 近期低频、金额较低 |
| 一般保持客户 | 低 | 高 | 低 | 历史频次较高、近期不活跃 |
| 一般挽留客户 | 低 | 低 | 低 | 较久未购买、次数与金额偏低 |

客户编号匿名化且没有联系方式。输出标签是分析结果，并不能直接发送营销信息。实际营销应加入退货复核、触达授权、成本预算和实验分组。

## 六、为什么还要使用 MySQL

SQL 展示数据库建模、窗口去重、分组聚合与独立核对能力。它还可发现 pandas 代码中错用行数、错分月份或错误过滤的情况。

项目先把**未清洗**的规范化数据导入 staging，而不是把 pandas 的最终结果导入后直接求和。SQL 使用：

```sql
ROW_NUMBER() OVER (
  PARTITION BY invoice_no, stock_code, description, quantity,
               invoice_date, unit_price_units, customer_id, country
  ORDER BY source_row
)
```

给完全相同的记录排序，再保留第一行。`CASE` 独立应用相同清洗规则。金额 `SUM`、订单 `COUNT(DISTINCT invoice_no)`、最近日期 `MAX(invoice_date)` 都由 MySQL 实际重新计算。

核对范围包括全部保留的源行、月份、订单、商品、客户指标、客户标签和含冲销月金额。金额内部为整数，要求相等，不用模糊误差容忍掩盖差异。

两者共同使用 Python 的类型规范化结果以及 RFM 分位点配置，因此不能说“从原始 Excel 到最终报告的所有环节都完全独立验证”。准确表达是：**SQL 独立验证清洗、聚合及评分应用结果**。

## 八、运营建议怎样才算有依据

“重要价值客户销售贡献高”是本数据可支持的描述。“给重要价值客户发优惠券一定增加销售”则缺乏证据。

可以设计待验证方案：在同类客户中随机抽出实验组和对照组，实验组收到某种服务或优惠，对照组保持原方式；提前约定观察 30 天，并比较复购、净贡献、优惠成本、退款和退订。只有实际实验结果才能说明是否有效。

本项目没有毛利、流量、广告、库存、联系方式或后续交易，不能给出利润率、转化率、真实流失率、预测准确率或已实现的营销增长数字。

## 九、答辩中常见问题

**为什么不把所有缺客户 ID 的行删掉？** 因为销售分析不要求客户身份，删掉会低估整体销售额；只有 RFM 需要识别客户。

**为什么 F 不是购买商品数量？** RFM 的 F 表示购买次数，使用不同订单数；商品数量是另一个指标。

**为什么不简单把金额最大客户定义成最有价值？** 一次大额交易可能是批发或随后冲销，RFM 结合近期性和频次，但仍需退货及利润校验。

**为什么 12 月下降不能直接解释？** 最后一个月只覆盖九天，没有完整月可比性。

**能否说完成了机器学习模型？** 不能。本项目是描述性分析与基于规则的 RFM 分层，没有训练预测模型。

**RFM 为什么不等于客户终身价值？** 它描述观察期历史行为，未估计未来现金流、利润和流失概率。

**分位数不是每档 20% 吗？** 连续、无并列值时近似如此；购买频次是离散值，大量并列时无法同时保证同值同分和人数均等。本项目优先同值同分。

**SQL 验证通过说明什么？** 说明两套实现按声明的规则得到一致结果，不能证明业务口径一定正确。口径仍需业务理解与源系统复核。
